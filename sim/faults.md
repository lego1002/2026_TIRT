# 故障注入處方箋

這份文件是模擬環境存在的**主要理由**。

你說「我怕自己不夠了解整個系統,真的出問題時找不出來」。找 bug 的能力沒辦法用讀的
學會 —— 只能靠「先看過症狀,再練習從症狀推回原因」。但在真車上等 bug 自己出現太慢、
太貴,而且出現時你同時面對硬體、網路、參數三層嫌疑犯,根本分不出是哪一層。

所以這裡把 `notes/` 裡記載過的每一個歷史 bug 都做成**一行指令就能重現**。做法是:

1. 挑一個處方,照著跑
2. **先不要看答案**,自己觀察 RViz 和 topic,寫下你認為的原因
3. 用「診斷」欄的工具驗證
4. 對答案

每一個都對應真車上真的發生過、而且花了很久才找到的問題。

## 1. 光達外參填錯 —— 地圖扇形塗抹

**真實事件**:2026-07-25。光達幾乎是反裝的(實測 +167°),`robot_bringup.launch.py`
的 `laser_yaw` 卻填 0。`tools/analyze_bag.py` 從直線段解出車在光達座標系的行進方向是
-167°,而 odom 說是 +0° —— 差了 167°。

```bash
./sim/gcs_sim.sh sim_laser_yaw:=2.9146
```

`sim_laser_yaw` 是光達**實際**裝的角度(物理現實),`laser_yaw`(TF 上宣告的)維持
預設 0.0 —— 兩者差 167°,和當時的真車一模一樣。

**你會看到**:開始遙控之後,地圖不是變成迷宮,而是一團扇形的塗抹。原地轉一圈特別明顯。

**為什麼**:SLAM 拿 TF 說的「光達朝前」去解讀「其實朝後」的掃描資料。odom 說車往前走,
光達看到的世界卻朝反方向流動 —— scan matching 每一步都在對抗一個近乎顛倒的運動模型。

**診斷**:
```bash
python3 tools/scan_match_check.py
```
⚠️ **不要看絕對的平均距離分數**。在 44cm 的走廊裡多數回波打在 0.2~0.5m 的牆上,
角度誤差在那個距離只有一兩格,平均值會被稀釋 —— 真車上 8~10° 的航向誤差只評到
0.039m,比 5cm 的格子還小,很容易被誤判成「正常」(這個工具自己第一版就是這樣判錯的)。
**判準是「有沒有一個明顯更好的位姿存在」**,不是分數大小。

**練習**:把 `sim_laser_yaw` 從 0 慢慢加到 0.3、0.6、1.5、2.9,看地圖從哪個角度開始壞掉。
你會發現大約 0.2 rad(11°)以內還看得出迷宮形狀,超過就開始糊 —— 這告訴你外參校準
需要準到什麼程度。

## 2. 里程計直線刻度沒校準 —— 地圖越畫越大

**真實事件**:韌體出廠的輪徑預設是 60mm,實際輪子是 48mm,速度多報 1.25 倍;
後來又發現板子的回授路徑根本不吃幾何設定,原始回授灌水 5~6.5 倍。

```bash
./sim/gcs_sim.sh odom_linear_error:=1.35
```

**你會看到**:地圖的走廊比實際長,繞一圈回到起點時,SLAM 畫的起點和實際起點對不上
(迴路閉合會硬把它拉回去,拉的時候整張圖會抽動一下)。

**診斷**:
```bash
ros2 topic echo /sim/odom_error      # 模擬獨有的上帝視角
python3 tools/odom_check.py          # 真車上用這支,它會直接算出該設多少
```

`/sim/odom_error` 是真車上**沒有**的東西 —— 真車只能用 `tools/odom_check.py` 開 1 公尺
再拿尺量。先在模擬裡看著 `/sim/odom_error` 理解「刻度錯 1.35 倍會累積成什麼」,
再去真車上練那個沒有上帝視角的版本。

## 3. 角度刻度錯 —— 轉彎後地圖整個轉開

```bash
./sim/gcs_sim.sh odom_angular_error:=0.6
```

**你會看到**:直線走都正常,一轉彎地圖就歪掉。轉越多次歪越多。

**為什麼**:麥輪的滾子打滑會摧毀輪速推算的角速度(真車實測:轉 360°,輪速卻報 2270°)。
真車的解法是改用陀螺儀積分航向(`use_gyro_heading:=true`),因為陀螺儀直接量角速度、
不受打滑影響。IMU 的四元數不能用 —— 6 軸沒有磁力計,yaw 是凍結的。

**練習**:這是迷宮比賽最致命的誤差來源。9x9 的迷宮要轉幾十個彎,每個彎差 2° 就會累積到
完全定位不能。試試 0.95(只差 5%),看繞完一圈之後偏多少。

## 4. 車子一頓一頓 —— 指令通道卡頓

**真實事件**:teleop 原本跑在筆電上,`/cmd_vel` 要穿越 WiFi。傳輸卡個幾百毫秒,
driver 的 watchdog(當時 0.5s)就把底盤歸零,下一筆到了又衝出去。

```bash
./sim/gcs_sim.sh cmd_stall_prob:=0.02 cmd_stall_sec:=1.5
```

**你會看到**:遙控時車子走走停停,但你的按鍵沒有任何問題。

**診斷**:
```bash
python3 tools/cmd_vel_check.py    # 報 /cmd_vel 到達間隔的 p50/p95/p99,以及幾次超過 watchdog
```
`ros2 topic hz` **看不出來**:平均 20Hz 很健康的資料流,還是可以每幾秒卡 0.8 秒。

**真車的解法**(已經做了):把 teleop 搬到 Pi 上跑,`/cmd_vel` 根本不過網路;
按鍵走 ssh(TCP,可靠)。另外 `cmd_vel_timeout` 0.5 → 1.0s、`/cmd_vel` 改 BEST_EFFORT。

**⚠️ 但是 Nav2 模式下這個問題會回來** —— Nav2 跑在筆電,`/cmd_vel` 又要過 WiFi 了。
試試:
```bash
./sim/gcs_sim.sh --nav cmd_stall_prob:=0.02
```
看 Nav2 在指令會卡頓的情況下表現如何。這直接關係到「Nav2 到底該跑在哪台機器」——
見 `sim/README.md` 的比賽架構分析。

## 5. 航向慢慢飄 —— 最難發現的那種

```bash
./sim/gcs_sim.sh odom_drift_deg_per_m:=3.0
```

**你會看到**:短距離完全正常,走久了才慢慢不對。地圖前半段很漂亮,後半段開始歪。

**為什麼難**:沒有任何單一時刻看起來是錯的。這是輪徑不等、地面不平、編碼器誤差累積的
綜合結果。SLAM 的 scan matching 本來就是為了修正這個而存在的 —— 所以**這個故障單獨開
其實不太會壞事**,真正的問題是它和其他故障疊加。

**練習**:先單獨開,看 SLAM 修得多好;再和 #1 疊加(`sim_laser_yaw:=0.3
odom_drift_deg_per_m:=3.0`),看 SLAM 什麼時候修不動。這會教你「SLAM 能容忍多少
里程計誤差」——答案是比你想的多很多,但前提是**光達外參要對**。

## 6. 加速就打滑 —— 高速時才出現

```bash
./sim/gcs_sim.sh --nav slip_on_accel:=0.25
```

**你會看到**:慢慢走沒事,Nav2 一加速就開始偏。

**為什麼**:麥輪的滾子在加速時最容易打滑,而 odom 是從輪子轉速算的 —— 輪子照轉,
車沒動,odom 不知道。

**真車的對策**:`notes/nav2_tuning.md` 明確寫了「如果起步/煞車會滑,**先降 `acc_lim_*`,
不要降 `max_vel_x`**」。麥輪打滑是加速度造成的,不是速度。試試把
`config/nav2_params.yaml` 的 `acc_lim_x` 從 1.5 降到 0.8,看是不是真的有效。

## 7. Nav2 說「沒有路徑」—— 幾何問題,不是規劃器問題

**真實事件**:2026-07-28,目標一下就 abort,車子完全不動,閒置時也沒有任何警告。
原因是 `robot_radius: 0.11` 太大 —— 膨脹後最大連通區只剩 4.07 平方公尺(0.10 時是 39.10),
車子**自己所在的格子就不可通行**,規劃根本沒開始。

這個不用注入,直接改參數:
```bash
# 1. 先確認正常狀態能走
./sim/gcs_sim.sh --nav

# 2. 另開一個終端,把半徑改大
#    編輯 config/nav2_params.yaml,兩處 robot_radius 都改成 0.13
#    然後在 nav 視窗 Ctrl-C、按 ↑ Enter 重跑(參數是 configure 時讀的,一定要重啟)
```

**診斷**:
```bash
python3 tools/costmap_check.py
```
它會告訴你車子自己的格子能不能通行、從那裡出發能到達地圖的百分之幾,以及
**這個迷宮到底容得下多大的 `robot_radius`**。

⚠️ 它的檔頭記載了一個讓這件事很難看出來的陷阱:`/global_costmap/costmap` 重新發布時
被**縮放到 0..100**(99 = 原始的 253 `INSCRIBED_INFLATED_OBSTACLE`,-1 = 未知),
所以拿 253/254 去比對永遠不會中,會讓一張四面都是牆的地圖看起來完全空曠。

**這在比賽場地特別關鍵**:走廊淨寬 44cm,車子約 15cm。`robot_radius` + `inflation_radius`
如果加起來超過 (44-15)/2 = 14.5cm,規劃器就會認為整個迷宮都不能走。

## 8. 同時有兩個 `map->odom` —— 定位莫名其妙很差

**真實事件**:2026-07-28,測試時筆電上的 `run_slam.sh` 還開著,它的即時 `/map`(168x142)
和 `map_server` 的存檔地圖(168x104)**同時**餵給 AMCL,兩個節點都在發 `map->odom`。
Nav2 完全不記任何 log,定位就是莫名其妙地爛。

```bash
# 建圖模式開著的時候,另開一個終端跑導航
./sim/gcs_sim.sh              # 視窗 1:SLAM
# 然後在 shell 視窗:
TIRT_SIM=1 ./run_nav2.sh sim_maze
```

**你會看到**:RViz 裡車子鬼影亂跳,AMCL 的粒子雲散開又收斂。

**診斷**:
```bash
ros2 topic info /map --verbose      # 有幾個 publisher?應該只有 1 個
ros2 run tf2_tools view_frames      # 看 TF 樹有沒有兩條 map->odom
```

`run_nav2.sh` 現在會在啟動自己的 `map_server` **之前**先問 `ros2 topic info /map` ——
那個時間點還有 publisher 就代表是別人的,它會警告。

⚠️ 另一個相關的坑:nav2 的 `component_container_isolated` **不理 SIGTERM**。真車上曾有
孤兒行程活了 20 分鐘、吃光 Pi 的 CPU,害下一次啟動沉默 46 秒沒有任何 log —— 看起來
完全像設定壞掉。所以 `run_nav2.sh` 用 SIGKILL,而且 kill pattern 是
`component_container_isolated.*nav2_container`,不是裸的 `nav2_container`(裸名字會
連操作者自己的 shell 一起殺,實機上發生過兩次)。

## 綜合演練:賽前總彩排

把幾個現實中一定會同時存在的小誤差疊在一起,看整套系統撐不撐得住:

```bash
./sim/gcs_sim.sh \
    sim_laser_yaw:=0.05 \
    odom_linear_error:=1.03 \
    odom_angular_error:=0.97 \
    odom_drift_deg_per_m:=1.0 \
    slip_on_accel:=0.1 \
    range_noise:=0.01
```

這些數字都是「校準得還不錯但不完美」的量級。如果在這個組合下還能掃出可用的地圖、
Nav2 還能走完 START → 中繼 → GOAL 而且不撞牆,那你的參數設定就有足夠的餘裕。

撞牆次數用這個看:
```bash
ros2 topic echo /sim/collision
```
規則五.5:**碰到迷宮牆面任一處即當次失敗**。目標是 0 次。
